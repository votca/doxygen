182 // for QMEwald. The periodic background reaches the Hamiltonian as a
183 // potential sampled on this grid, which the DFT engine integrates
184 // against the density.
185 //
186 // There used to be a second route, handing the engine multipole
187 // moments and k-vectors to build its own AO matrices from, gated by a
188 // second flag. Nothing ever set it up -- the legacy jobcalculator that
189 // once did was removed -- so it has been deleted along with the
190 // machinery behind it (DFTEngine's IntegrateEwald* helpers, the
191 // AOEwald* matrices, the ewaldcontainer types). Two things are worth
192 // recording about that, since the decision was to remove code that had
193 // been deliberately kept:
194 //
195 // - It was blocked anyway. A rank-1 (induced dipole) source needs
196 // operator-centre derivatives from libint2, which is why
197 // AOEwaldRealSpaceDipoles was never instantiated even from the dead
198 // path -- the real-space route split every dipole into a pair of
199 // point charges instead.
200 // - It would not have been the faster route in any case. It replaces
201 // a loop over grid points (linear in QM size) with one over shell
202 // pairs (quadratic), so it wins only for small QM regions -- the
203 // opposite of what it was being kept for.
204 //
205 // Recoverable from the git history if either of those ever changes.
206 //
207 // ONLY ITS POINTS AND VALUES ARE VALID. PrepareEwaldPotentialGrid
208 // builds this grid against a BasisSet, an AOBasis and a QMMolecule
209 // that are all locals of that function, and GridBox::
210 // FindSignificantShells stores raw `const AOShell*` into the basis it
211 // is handed (gridbox.cc, addShell(&store)). Those shells die with the
212 // function, so from the moment PrepareEwaldPotentialGrid returns this
213 // object holds dangling pointers.
214 //
215 // What remains safe is everything that does not follow them:
216 // getGridpoints, getPotentialValues, getBoxesSize, GridBox::size.
217 // CalcAOValues, Matrixsize, AddtoBigMatrix and anything else touching
218 // significant_shells is undefined behaviour. That is why the grid is
219 // never integrated on here or in QMPackage, and why DFTEngine rebuilds
220 // its own from grid_name_ and copies only the values across -- see
221 // dftengine.cc.
222 //
223 // Nothing dereferences them today. The public Vxc_Grid& accessor that
224 // used to sit next to copyEwaldGrid() was removed because it handed
225 // this object out with no way to know that, and had no callers.
226 // Giving the basis a longer life would remove the hazard, but it buys
227 // nothing on its own: the transport is by value either way, and
228 // DFTEngine has to integrate against the AO ordering of its own
229 // dftbasis_ regardless.
230 Vxc_Grid ewaldgrid_;
231 bool ewald_grid_ready_ = false;
232 // Whether the background's potential has already been laid down on that
233 // grid. Separate from ewald_grid_ready_ because the grid is built once
234 // and the potential is evaluated once, but for different reasons: the
235 // grid because geometry and basis are fixed, the potential because the
236 // background is frozen. See InteractwithEwaldRegion.
237 bool ewald_potential_evaluated_ = false;
238 // sum_A Z_A phi(R_A). The grid carries the potential the ELECTRONS
239 // feel; the nuclei sit in the same potential and have no other way in.
240 double ewald_nuclear_energy_ = 0.0;
